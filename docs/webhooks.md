# Webhooks

A webhook wakes an agent when something happens to its role, for example when a task is assigned to it. Webhooks are off by default. Only the owner configures them, in the web interface (**More → Webhooks**); they are not available through MCP.

The request carries only a signal: which events happened, for which role, and when. The receiving agent fetches the content itself through MCP (`start`, `get`, `changes`), so nothing from the workspace leaves the service in a webhook.

## Configuring

For each webhook choose:

- **Role**: whose events wake the receiver.
- **URL**: where the POST goes. It must use `https` and point to a public address; see [Address restrictions](#address-restrictions).
- **Authorization header** (optional): sent verbatim as `Authorization`, for receivers that expect a key, for example `Bearer <key>`. It is stored encrypted and never shown in full again.
- **Events**: at least one of the events below.

Each webhook gets its own signing secret, generated by the service. The web interface shows it on request so you can configure the receiver to verify signatures. A **Send test** button queues a delivery whose only event has the type `test` and id `0`, and the delivery log shows the last attempts with status codes and errors. A webhook can be disabled without deleting it.

## Events

| Event | When |
| --- | --- |
| `task.assigned` | A task is created with this role, or moved to this role. |
| `task.updated` | A task of this role changes (status, fields, claim). |
| `task.commented` | Someone comments on a task of this role. |
| `task.unblocked` | The last unfinished dependency of a task of this role is done. |
| `role.updated` | The role itself changes, including its instruction. |

## Delivery

- Events for the same webhook within **10 seconds** are coalesced into one request.
- Each attempt times out after **10 seconds**. Any `2xx` response counts as delivered.
- Failed attempts are retried after 30 seconds, 2 minutes, 10 minutes, 30 minutes and 2 hours: **6 attempts** in total. After that the delivery is marked failed.
- Redirects are not followed.
- The delivery is queued in the same database transaction as the change, so a restart does not lose it.

## Request

```http
POST /your/path HTTP/1.1
content-type: application/json
x-workspace-delivery: dlv_…
x-workspace-event: task.assigned
x-workspace-timestamp: 1795000000
x-workspace-signature: sha256=5d1c…
authorization: Bearer <your key, if configured>

{
  "delivery_id": "dlv_…",
  "type": "task.assigned",
  "event_id": 42,
  "role_id": "role_…",
  "role": "developer",
  "at": "2026-11-25T10:00:00.000Z",
  "events": [{ "id": 41, "type": "task.updated", "at": "…" }, { "id": 42, "type": "task.assigned", "at": "…" }],
  "sent_at": "2026-11-25T10:00:10.000Z"
}
```

`type`, `event_id` and `at` describe the latest event; `events` lists every coalesced event. `event_id` can be passed to the MCP `changes` tool as a cursor (minus one) to read exactly what happened.

## Verifying the signature

The signature is an HMAC-SHA256, hex-encoded, of the timestamp, a dot and the raw request body, keyed with the webhook's signing secret:

```text
x-workspace-signature = "sha256=" + hex(HMAC_SHA256(secret, timestamp + "." + raw_body))
```

Reject requests whose timestamp is more than five minutes away from your clock, and compare signatures in constant time. Example in Node.js:

```js
import { createHmac, timingSafeEqual } from 'node:crypto';

export function verify(secret, headers, rawBody) {
  const ts = headers['x-workspace-timestamp'];
  const sig = headers['x-workspace-signature'] ?? '';
  if (!ts || Math.abs(Date.now() / 1000 - Number(ts)) > 300) return false;
  const expected = 'sha256=' + createHmac('sha256', secret).update(`${ts}.${rawBody}`).digest('hex');
  return sig.length === expected.length && timingSafeEqual(Buffer.from(sig), Buffer.from(expected));
}
```

Receivers that cannot check signatures can rely on the Authorization header alone.

## Address restrictions

By default the service refuses webhook URLs that point to loopback, private, link-local, carrier-grade NAT, multicast or other non-public addresses. The check runs on every resolved address at connection time, so a DNS name that later resolves to an internal address is refused too. Set `WEBHOOK_ALLOW_PRIVATE_ADDRESSES=true` only if the receiver really runs on your own network; it also allows plain `http` URLs.

## Example receiver: a Grok Bot routine

A Grok Bot routine with a webhook trigger accepts an HTTP POST with `Authorization: Bearer <key>` and an optional JSON body, and answers `200` when a run has started; each routine runs at most 200 times an hour ([Grok Bot routines](https://cursor.com/help/grok-bot/routines), checked on 25 November 2026). To wake such a routine:

1. Create the routine with a webhook trigger and copy its URL and key.
2. In **Webhooks**, add a webhook for the role the routine plays, with that URL and `Bearer <key>` as the Authorization header, and choose the events.
3. In the routine's prompt, tell it to call `start` with its role and work from there.

Coalescing keeps a burst of changes to one run, well under the routine's hourly limit.
